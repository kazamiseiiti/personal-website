# 使用 Codex 做了第一个个人博客

## 为什么突然想做一个个人博客

几年前查文献的时候，就看到了别人的个人博客，再加上我是零几年互联网最鼎盛的博客时期成长而来的，所以一个只属于自己的个人网页一直是我想做的。小时候看别人的博客，还有看到那些浏览过博客的留言的人，我就觉得很帅气了。

但是奈何博主大学本科时期虽然修了几年CS但完全没有这方面的内容，只有无尽的C语言，分叉树，Java, Racket这种原理级别的知识，完全没接触过web开发，当然也可以说我懒没有自学......

到了读硕士的时候我又因自身兴趣去专攻了深度学习与医学图像处理。所以我对制作博客可谓是一窍不通。多亏了ChatgptPlus给的免费额度，终于是乘上了时代的洪流制作出了第一个属于自己的网站和博客。

这篇文章一方面是测试发布另一方面对此次工程的小总结。
## 从 Git 仓库开始

基础中的基础，先本地部署项目然后连接GitHub。

这个部分只要不是完全没碰过Git应该都已经很熟练了。
## 第一次翻车：Build 全绿，浏览器还是红了

这是我第一次比较认真地让 Agent 从头到尾做一个小项目。

开工之前我还挺谨慎的，先到处搜怎么省 Token、怎么让 Agent 少犯傻、怎么把任务说清楚，最后把搜到的东西一股脑丢给 ChatGPT，让它帮我搞了一版看起来很专业的 Prompt。

然后 Codex 就开始干活了。

搭项目、建页面、做三语言，顺手把 typecheck、lint、build 全跑了一遍。

最后告诉我：都没问题。

居然这么顺利，这不正常。

果不其然浏览器一打开，Error。

问题出在主题切换上。最离谱的是，typecheck 没事，lint 没事，build 也没事，偏偏真正跑起来还是报错。

果然“build 过了”基本就代表能用了，根本不是这么回事。

更搞的是，第一次让 Codex 修，它也只是把原来的裸 `<script>` 换成了 Next.js 的 `<Script>`。看起来像是改正规了，实际上页面一刷新，错误还在。

第二次才算真的往结构上查，最后发现是 Root Layout 和 Locale Layout 的职责混在一起了。把主题初始化挪到真正的 Root Layout 之后，这事才算彻底消停。

还是得自己打开网页看看。
## 为什么我后来换成 VS Code + Codex CLI

最开始我用的是 Codex 桌面端。

能干活是能干活，但我发现看不到它到底执行了哪些命令、改了什么、为什么这么改。

我心痒难耐。

于是咨询了一下 ChatGPT，最后换成了 VS Code + Codex CLI。

这中间还经历了 Node.js、npm、pnpm、PowerShell Execution Policy 之类的环境配置。

环境配置这种东西果然是无论干什么都逃不掉的。

总之最后成功在终端里跑起了 Codex，也终于能比较清楚地看到它读了哪些文件、跑了哪些命令、哪里报错、怎么修改。

舒服了。
## 额度怎么掉得这么快

真正把我吓到的是额度。

最开始一个比较大的页面开发和排错任务，5 小时额度直接掉了 41%。

我当时第一反应就是：

我草，做个博客怎么这么费。

后来想想其实也正常。

一个 Agent 任务里，它不只是“写几行代码”，还会不断读取项目上下文、执行工具、跑 typecheck、lint、build，再根据结果继续修改。

如果一个任务范围特别大，上下文又一直累积，额度掉得当然飞快。

这时候之前在 Vercel Agent Harness 课程里看到的 Context Management，突然就不再是一个很抽象的词了。

它真的会直接反映在你的额度上。
## 我后来怎么改自己的工作方式

后来我开始刻意限制 Codex 的工作范围。

比如：

修 Bug 就只修 Bug。

做首页就只做首页。

调配色就只调配色。

能自己在浏览器里点两下确认的，就不让 Agent 花额度替我点。

还有一点就是 Prompt 要尽量精准且致命，让它没有太多多余的操作空间。

要让他明白：

这次要做什么、不做什么、做到什么算完成、最后怎么验证。

这其实也是一种能力，只能慢慢积累。
## 这个网站是怎么慢慢成形的

后面的工作使用AI Agent就轻松很多了。

调调颜色和主题，修改一下个人简介，然后再根据自己的鬼点子再加入点东西，网站就一点点成型了。

做到这里理解了HR招聘时”用AI Agent做网页“为什么会不认为是个项目，

太简单了。

和以前那种自己从头写，自己查文档，一点点查bug调参相比门槛低了太多。
## 回头再看 Agent Harness

他说的很多东西实际上在我之前用ChatGpt来帮助我研究和查错误时就有类似的经验了。

只不过在AI Agent的过程中需要你为工程的全部结构考虑，在考虑清楚整个工程所需要的工作内容，意外情况处理，整体结构之后再输出你的需求。

比如这个不能碰，验证怎么做，出了意外怎么处理，结构怎么拆分。

思考的深度比以前高了很多。

当然这需要你熟练以及逻辑清楚。
## 最后

Vibe Coding确实是一项伟大的创造，解放了码农的生产力，但我觉得让工程师们更两极分化了。

决定效率的不应该是背的滚瓜烂熟的固定代码，应该是思维逻辑的清晰与否。
